> 走查方式：**真实点击**（非只读浏览）。用 Puppeteer + 无头 Chrome 按评审的操作方式逐个点按钮，对 90 项断言做自动比对。
> 走查脚本**随仓库交付**：[`tools/walkthrough.js`](../tools/walkthrough.js)，运行方式见 [`tools/README.md`](../tools/README.md)
> （`cd tools && npm install && node walkthrough.js`，原型需已在 8080 运行）。评审可自行复现，不必采信本文件的自述。
> 最近一次结果：**90 通过 / 0 失败，全程无 JS 报错**。

## 二、走查中发现并修复的缺陷

走查不是走过场 —— 以下真实缺陷都是走查抓出来并已修复的：

| # | 缺陷 | 严重度 | 修复 |
|---|---|---|---|
| 1 | **E1「让女儿帮我安排」直接完成了绑定，跳过了 E2 授权页** —— 用户没看到"女儿能看到什么"就同意了，与产品说明 §1.2 的权限透明要求相悖 | 高 | E1 改为跳转 E2，由 E2 的「同意连上」才真正建立协作 |
| 2 | **语音复述取值错误，页面显示 `[object Object]`** —— `VOICE_SCRIPTS` 里 `good/fixed/fixedNo` 存的是对象却按字符串输出 | 高 | 在 `voiceScript()` 统一归一化为字符串 |
| 3 | **截止型事务不区分紧急程度**：缴水费（10/15 前）也被标成红色「今天到期」，与事实不符 | 中 | 增加 `urgent/daysLeft` 字段；紧急的标「今天到期」，不紧急的标「还剩 N 天」 |
| 4 | **`?fail=2` 不带 `step` 参数时不会进入"连续听不清"状态**，与页面清单声明的直达路由不符 | 中 | 无 `step` 且 `fail>=2` 时自动进入 fail 状态 |
| 5 | **老人端首页缺少"女儿已经回话了"回执横幅** —— 女儿回应后老人切回首页看不到任何提示，必须自己翻回求助页，与产品说明 §3.3「女儿回应 → 老人端弹回执」不符 | 高 | 在 E3 首页补回执横幅（点进 E12），并在 E4 详情补「看女儿的回话」入口；新增走查路径 5 长期守住 |
| 6 | **老人取消事务时，未回应的求助没有被撤回** —— 家属端仍挂着「妈妈找你帮忙」红色横幅，且仍可回应；违反"取消的事务不能仍显示已发送成功" | 高 | `Store.cancelTask` 检查待处理求助并一并撤回；E9 明确告知；家属端改显示「妈妈撤回了求助」；走查路径 6 长期守住 |
| 7 | **老人拒绝授权被静默覆盖** —— E1「我自己来」/ E2「先不连」后 `seedFor()` 仍把 `linked` 强制置 `true`，未授权时家属端能看到全部事务 | 高 | 引入 `linkDecision` 状态：老人明确拒绝后不再自动连接；家属端在未建立协作时显示空状态 |
| 8 | **E17 关闭共享项后家属端无任何变化** —— F1 仍列事务、F7 仍有趋势、F5 仍有改期入口 | 高 | F1 / F7 / F5 渲染前读取 `Store.state.share`，关闭项替换为带说明的空状态 |
| 9 | **F8「请求已被撤回」在流程内没有入口** —— 只能手动改地址栏访问，家属端看不出发生过求助 | 中 | F1 增加「妈妈撤回了求助」可点击横幅（复用 `lastWithdrawn` 字段，原先是死代码） |
| 10 | **E8 老人说想加一件事后流程断掉** —— 提示"已转给女儿"，但家属端没有任何对应待确认项 | 中 | 新增 `elderAdd` 状态：F1 出现「妈妈想加一件事」→ F3（`?src=elder`）确认 → 老人端出现新待办 |
| 11 | **F7「加一句妈妈常说的话」点了没效果** | 低 | 改为输入框 + 「加进去」，真实写入 `phrases` 并立即出现在列表 |
| 12 | **F4「▶ 点这里听」不可点击**；**E17「怎么用」只弹提示没有画面**；**控制条 ③⑧ 未真正直达** | 低 | F4 改为可点按钮并给播放提示；E17 改为完整弹窗说明；③ 改指 `?step=result`、⑧ 改指 `?step=listening` 自动推进 |
| 13 | **家属端「记录」与真实操作无关** —— `events` 只写不读 | 低 | F7 新增「妈妈那边的动态」区块，直接渲染演示中的真实操作 |

> 开发期另发现一处路由缺陷（`parseHash` 把 `:id` 拼进了路由 key，导致所有带 id 的页面都落到默认首页），在原型图截图阶段发现并修复，未进入走查环节。

## 三、已知限制（走查覆盖不到的）

- 计时、"30 分钟未回应"等由控制条/直达路由触发，**没有真实的 30 分钟等待** —— 这是刻意的，评审不可能等 30 分钟。
- 语音识别结果、女儿留言、AI 建议均为预设内容（见《03-演示说明.md》§七 的逐条标注）。
- 未覆盖任意输入：原型只保证《02-页面与状态清单.md》§三 列出的 15 个案例路径内的操作成立。
- 走查脚本需要本机有 Chrome 与 Node（`cd tools && npm install`）。这只影响"复现走查"，
  **不影响评审演示**：演示只需要 Docker，或任意静态服务器。

## 四、Docker 演示实测记录

评审的实际入口是 `docker compose up --build`，所以这一项单独实测并留证。

**环境**：Docker 29.8.2、Docker Compose v5.5.1、Windows 11 + Git Bash。

| 步骤 | 命令 | 实际结果 |
|---|---|---|
| 1 | `docker compose up --build` | 镜像 `anan-elder-prototype:1.0.0` 构建成功（基于 `nginx:1.27-alpine`，无编译步骤） |
| 2 | `docker compose ps` | 容器 `anan-elder-prototype` 状态 **Up (healthy)**，端口 `0.0.0.0:8080->80/tcp` |
| 3 | `curl -I http://localhost:8080/` | `200` |
| 4 | `curl http://localhost:8080/css/app.css` | `200` |
| 5 | `curl http://localhost:8080/js/app.js` | `200` |
| 6 | 容器内静态文件 vs 仓库 HEAD 逐文件比对 | `index.html`、`css/app.css`、`js/*.js` **完全一致**（无"容器跑的是旧版本"问题） |
| 7 | 对该容器执行 `tools/walkthrough.js` | **57 项断言全部通过** |

> 结论：`docker compose up --build` → 打开 `http://localhost:8080` → 按《03-演示说明.md》走完演示，
> 这条链路已在真机验证，不再是未验证项。
>
> 一处已知的容器命名约束：`docker-compose.yml` 未固定 `container_name`，避免与本机可能存在的
> 同名容器冲突；若 8080 被占用，改 `docker-compose.yml` 里的 `"8080:80"` 左值即可（见 README 第八节）。
