# 安安 · 独居老人生活事务提醒与家人协作 —— 产品说明

> 考核方向：PRODUCT（2026 秋季）｜题目：面向老年人的 AI 日常事务与家庭协作助手
> 本文档为单一入口的结构化说明：用户与需求依据 → 范围与取舍 → 信息架构 → 核心功能 → AI 规则 → 指标与验证。
> 页面清单见《02-页面与状态清单.md》，操作指引见《03-演示说明.md》，走查见《04-走查记录.md》。

**一句话定位**：让不会用智能手机的老人"听得懂、点得动、有人接手"地完成每天那几件必须做的事，并让外地子女只在需要时被叫到。

## 一、用户与需求依据

### 1.1 锁定的老人与家庭情况（具体，不泛化"所有老年人"）

**老人端用户：张桂兰，72 岁，独居**

| 维度 | 具体情况 | 对设计的影响 |
|---|---|---|
| 居住 | 独居，子女定居外地，每周视频通话 1 次，无法实时跟进日常琐事 | 日常提醒必须由系统承担，家属只做兜底 |
| 身体 | 高血压（**每日早晚 08:00 / 20:00 服降压药**）；轻度关节炎，出门买菜、取快递体力有限 | 事务有**每日循环型**和**截止日型**两种节奏，提醒逻辑要分开 |
| 设备能力 | 只有一台智能手机，**仅会接打电话、用微信发语音**；不会打字、看不懂复杂 App 和长文字通知、手动设闹钟操作困难 | 主输入=语音+大按钮；**无键盘输入、无复杂表单**；正文 ≥ 28px、对比度 ≥ 4.5:1、主按钮高度 ≥ 72px |
| 记忆 | 经常记错吃药时间、错过缴费截止日期、忘记去驿站取快递 | 需要"该做什么 + 什么时候截止 + 没做会怎样"三件事同时讲清楚 |
| 心理 | 怕"点坏了"、怕麻烦女儿、对弹窗广告高度警惕 | 每一步都有"不会弄坏"的反馈；无广告；求助不制造愧疚感 |

**家属端用户：张莉，40 岁，女儿，在外地城市工作**

| 维度 | 具体情况 | 对设计的影响 |
|---|---|---|
| 时间 | 工作日会议密集，午休与晚间有空 | 通知要**聚合、可延后处理**，不能做成夺命连环 call |
| 能力 | 智能手机熟练用户 | 家属端可承担"录入待办"这种复杂操作，替老人省掉 |
| 心理 | 想远程帮老人规划每日待办、收到**完成/未完成**反馈，但不希望频繁打电话打扰老人 | 默认只推**异常**；正常完成只进日志，不打扰 |

### 1.2 老人的需求 ≠ 家属的诉求（必须区分，不合并为"家庭需求"）

| | 张阿姨自己要的 | 女儿想要的 |
|---|---|---|
| 核心 | 到点有人提醒我吃药、取快递、交水费；忘了不慌 | 能远程帮妈妈把待办**录入好**，不用妈妈自己操作 |
| 次要 | 不想老麻烦女儿；能听懂、看得懂、点不坏 | 只在**异常**时被找；能看到完成/未完成反馈 |
| 反面 | 不要被追问"你为什么没做" | 不要收到"妈妈已完成"这种正常流水刷屏 |

→ 设计后果：**复杂操作全部放在家属端（录入/改期），老人端只做"听提醒 + 语音回话 + 求助"**。家属默认看不到位置、通话、其他 App；家属改待办时间必须经老人确认。

### 1.3 需求依据：真实观察、二手资料与假设的区分

#### A. 二手资料（有真实来源，已核实）

| 事实 | 数据 | 来源 |
|---|---|---|
| 老年人口规模 | 截至 2024 年末，全国 60 周岁及以上人口超 3.1 亿 | 民政部、全国老龄办《2024 年度国家老龄事业发展公报》 |
| 独居老人占比 | 全国独居老人比例达 14.2% | 《第五次中国城乡老年人生活状况抽样调查基本数据公报》 |

#### B. 替代方案实际体验（2 个，附来源与本方案改进）

**① 苹果「健康」App —「药物」功能（iOS 16 起，iOS 26 含用药历史）**

- 体验方式：在 iOS 设备上实际添加一种每日两次药品并接收提醒（复现路径：健康 App → 浏览 → 药物 → 添加药物）。
- 做得好的：30 分钟内未确认会发**跟进提醒**；可从通知直接标记"已服/已跳过"；iOS 26 有依从历史。
- 观察到的**不足**：① **没有家属协同** —— 错过提醒不会有任何人被通知（YouGot 对 Siri/健康生态的分析同样指出"无法通知照护者"）；② 无药量余量追踪、无宽限期窗口；③ 入口在「健康 → 浏览 → 药物」三层深处，对不熟 iOS 的老人几乎不可达。
- 对本方案的影响：**把"超时未完成 → 通知家属"做成一等公民**，而不是靠老人自己打电话；提醒入口做成首页大卡片，不藏在层级里。

**② 微信「关怀模式」+ 手机自带「时钟/提醒事项」**

- 体验方式：在安卓（MIUI 大字模式）与 iOS（提醒事项）上分别设"每天 08:00 吃降压药"，观察老人视角的实际使用。
- 做得好的：关怀模式确实把字放大了；提醒事项免费、稳定。
- 观察到的**不足**：① 提醒事项**没有"已做/没做"概念**，只是一条待办，点掉就消失，无法回看"今天到底吃没吃"（Cadence 对 iOS 提醒事项的评价："a general-purpose to-do list doing the job of a specialised tool"）；② 关怀模式只放大字体，**不简化任务结构** —— 央视网《锋面》与人民日报健康的实测都指出"首页大字、二级页面原样"是普遍问题；③ 文案是系统语言（"重复""snooze"），不是老人语言。
- 对本方案的影响：① 状态必须**可回看、可被家属看到**；② 任务结构从"设一个闹钟"改成"三步确认"（听到 → 做了 → 说一声）；③ 全部文案用老人自己的话（"该吃药了"而不是"用药提醒"）。

#### C. 尚未验证的假设（明确标注，不写成证据）

| 假设 | 为什么暂时是假设 | 验证方式 |
|---|---|---|
| H1 独居老人愿意让子女看到自己的事务完成状态 | 未做真人访谈（48 小时内不强制） | 上线后用"共享开关"的实际开启率验证 |
| H2 语音是老人端的主导输入方式 | 依据是"只会发语音"的画像推演，非实测 | 用过程指标"AI 识别纠错率"与语音/按钮使用占比验证 |
| H3 家属更愿意"异常才打扰"而非"每日播报" | 女儿画像的推演 | 家属端 A/B：异常通知 vs 每日摘要的关闭率 |
| H4 30+30 分钟的两级升级节奏合适 | 纯设计参数，无数据 | 后台看"二次提醒后确认"的占比再调 |
| H5 老人愿意让女儿替自己录入待办 | 涉及"被管着"的感受，推演不稳 | 观察"老人主动请女儿添加"与"老人自己在 E15 发起"的比例 |

> 说明：本方案**没有**把任何 AI 生成的访谈记录、用户评价或调研结论当作真实证据。以上 A、B 为可查证的二手资料与真实产品体验，C 为待验证假设。

## 二、范围与取舍

### 2.1 本次必做范围（足以走完一个有价值的用户流程）

围绕 **"生活事务提醒"** 这一个主问题，覆盖四种事务形态：

| 事务 | 类型 | 提醒节奏 |
|---|---|---|
| 服降压药 | 每日循环 | 每天 08:00、20:00 |
| 去驿站取快递 | 截止型 | 快递到驿站后 3 天内，截止前一天与当天提醒 |
| 缴水费 | 每月截止 | 每月 15 日前，10 日与 14 日提醒 |
| 周二买菜 | 每周循环 | 每周二 09:30 |

必做能力：

1. **家属语音录入待办**：女儿说一句"每天早上八点和晚上八点吃降压药"，AI 识别成结构化待办，家属确认后生效（含识别纠正）。
2. **AI 按时语音提醒老人**：到点全屏 + 语音播报，无键盘、无层级。
3. **老人语音反馈完成状态**：复述确认，识别有误可纠正，也保留大按钮直接确认。
4. **状态同步**：正常完成 → 家属端日志（不打扰）；超时未完成 → 推送提醒给子女。
5. **老人主动求助**：一条事务卡住时一键"叫女儿帮忙"。
6. **家属回应**：留言/打电话/改期/确认，老人收到回执。
7. **老人取消/请假**、**家属未回应的兜底**、**网络失败**。
8. **关键状态全覆盖**（见 02 文档状态清单）。

### 2.2 主动舍弃的功能及理由

| 舍弃项 | 理由 |
|---|---|
| 智能药盒硬件、跌倒检测、定位监控、紧急呼叫 120 | 超出"一个日常事务"的考核边界；安全类功能责任重大，不在原型验证范围 |
| 医学剂量建议、药物相互作用提示 | 有真实安全风险，原型不应给出任何医学判断 |
| 陪聊/情感陪伴平台 | 题目明确不要求完整陪聊平台 |
| 真实网购/代购、线上缴费支付 | 涉及真实交易与资金，超边界；只做"提醒 + 完成反馈" |
| 多老人管理（同时管父母/岳父母） | 单流程足够，多人会稀释核心路径 |
| 真实短信/电话/微信推送、真实语音识别 | 原型用预设状态模拟，演示说明中逐条标注 |

> 范围检验：以上必做项合起来，老人可以从"听到提醒 → 语音回话 → 出问题 → 求助 → 得到回应 → 回看历史"走完**一个完整且有价值的流程**，不是只剩一个输入框加一张结果页。

### 2.3 最值得验证的下一步（只写一个）

**H4（两级升级节奏 30+30 分钟）的真实分布** —— 若数据显示大部分漏做在二次提醒后才被处理，则把家属通知提前到一次未确认后 45 分钟。

## 三、信息架构

### 3.1 老人端（单列、大字、无 tab 嵌套，底部 3 个超大按钮）

```
首页（今日待办卡片，按时间排序）
 ├─ 点卡片 → 提醒详情
 ├─ "我做完了" / "用语音说" → 确认完成
 ├─ "叫女儿帮忙" → 求助 → 等待 → 结果
 ├─ 底部「历史」→ 本周记录
 └─ 底部「设置」→ 字体大小 / 语音播报 / 共享给女儿的开关 / 找女儿帮忙
```

### 3.2 家属端（常规信息密度，底部 3 个 tab）

```
首页（今日状态总览 + 异常通知）
 ├─ 「添加待办」→ 语音录入 → AI 识别复述 → 确认/纠正
 ├─ 点异常 → 请求详情 → 回应（留言/打电话/改期/确认）
 ├─ 「共享」tab → 权限清单 + 待确认事项
 └─ 「记录」tab → 一周趋势 + 家庭成员状态
```

### 3.3 主流程（核心路径）

```
[家属语音录入待办] → AI 识别复述 → 家属确认 → 待办生效
        ↓
[到点] → 老人端全屏提醒 + 语音播报
   ├─ 老人点"我做完了" 或 语音说"已经吃过药了"
   │      → AI 复述确认 → 状态=已完成 → 家属端日志（不推送）
   └─ 30 分钟未确认 → 二次提醒
        ├─ 仍未确认（到点后 60 分钟）→ 系统通知女儿 + 老人端提示"已告诉女儿"
        │     ├─ 女儿回应（留言/电话/改期）→ 老人端弹回执"女儿回话了"
        │     └─ 30 分钟女儿未回应 → 老人端显示"女儿还没看到" + 替代方案（打电话给女儿/社区医生）
        └─ 老人主动点"叫女儿帮忙" → 等价于上面的系统通知，但由老人发起
```

## 四、核心功能说明（1 个）

### 「生活事务提醒 + 超时家人协作」

| 项 | 内容 |
|---|---|
| 用户目标 | 老人：到点把该做的事做了、不吃漏不错过；家属：异常时知道并帮上忙 |
| 输入 | 家属端：语音录入待办；老人端：语音/按钮反馈完成状态 |
| 输出 | 老人端：今日待办卡片、确认结果、求助进度、女儿回执；家属端：识别结果确认页、异常通知、请求详情、回应入口、一周趋势 |
| 页面行为 | 见《02-页面与状态清单.md》E1–E17 / F1–F9 |
| 状态变化 | 未提醒 → 已提醒未确认 → 已确认 / 升级通知家属 → 家属已回应 / 家属未回应 → 已解决；取消 = 求助撤回，状态回到"已提醒未确认" |
| 业务规则 | ① 到点 30 分钟未确认 → 二次提醒；60 分钟仍未确认 → 通知家属（老人端同步告知，不偷偷通知）② 老人主动求助与系统通知等价，但老人发起的会写明"是我请女儿帮忙的" ③ 家属改期/改时间必须经老人确认，改后老人端有"已修改"回执，老人没确认前老人端时间不变 ④ 取消求助后家属端显示"已撤回"，不能再回应；老人把事务改成"今天不做"时，未回应的求助**一并撤回**，两端状态一致 ⑤ 家属未回应 30 分钟后，老人端给出替代方案而不是无限等待 ⑥ 缴费/取快递这类**截止型**事务，截止前一天额外提醒一次 ⑦ 老人在「设置」里关闭的共享项，家属端**立即**看不到对应内容（首页事务清单 / 一周趋势 / 改期入口同步消失）；老人拒绝建立协作时，家属端只显示"尚未建立协作"空状态 |
| 异常处理 | 识别失败 → 语音页给"再试一次 / 改用按钮"两个出路，不让老人卡死；网络失败 → 确认按钮置灰并提示"没连上网，稍后再试"，数据不丢；女儿未回应 → 不静默，明确告知并提供替代 |

## 五、AI 规则

### AI 介入点 1：家属端语音录入待办（把复杂操作从老人身上拿走）

| 项 | 内容 |
|---|---|
| 介入步骤 | 女儿在 F2 按"说一句"录入待办后 |
| 使用信息 | 仅本次语音内容；不读取位置、通讯录、其他 App |
| 呈现方式 | **结构化复述 + 原文对照**："识别结果：取快递，时间：10 月 7 日 10:00。"下方并列显示原始语音（可回放，模拟）与识别出的字段（事项/时间/重复规则），每项都可改 |
| 用户纠正 | 提供「修改时间」「修改事项」「删除该识别」三个入口；全部点选/滑动，不打字 |
| 失败/不可信处理 | 完全没听清 → 显示"我暂时没有理解清楚"，**保留原始语音**，并提供手动填写入口；置信度低 → 不猜，把两种理解都列出来让家属选；识别结果**必须家属确认才生效**，不会直接写进老人端 |
| 明确不做 | 不做自由对话；不做医学判断；不在家属未确认前下发提醒 |

### AI 介入点 2：老人端语音反馈完成状态（核心）

| 项 | 内容 |
|---|---|
| 介入步骤 | 老人在确认页点"用语音说"后 |
| 使用信息 | 仅当前事务名 + 计划时间（如"今天早上那顿降压药"），**不读取**位置、通讯录、其他 App |
| 呈现方式 | 必须先**复述**："我听到的是——今天早上的降压药，已经吃好了。对不对？"配"对"/"不对"两个大按钮，识别结果**不直接写状态** |
| 用户纠正 | 点"不对"→ 进入纠错编辑页：大字列出几个候选（换一句说 / 我来按按钮），点一下即可，无需打字 |
| 失败/不可信处理 | ① 完全没听清 → 显示"我暂时没有理解清楚"，**保留原始语音**，连续 2 次失败后自动出现"改成按按钮"大按钮，不让老人卡死；② 置信度低（如把"吃了"听成"没吃"）→ 不猜，复述时把两种理解都列出来让老人选 |
| 家属端如何参与 | 家属端 F6 可看到"妈妈刚才那句话系统听成了 XX，已纠正为 YY"的记录，并可帮妈妈改说法；AI 听不懂时家属可把常用说法加进"妈妈的话"清单 |
| 明确不做 | 不做自由对话；不做医学判断；识别失败不无限重试 |

### AI 介入点 3：家属端"改期建议"（辅助，演示用）

| 项 | 内容 |
|---|---|
| 介入步骤 | 家属端「记录」tab，当出现规律时（演示：连续 3 天晚上的药都 20:40 之后才确认） |
| 使用信息 | 仅老人端事务确认的时间戳与结果，不使用其他数据 |
| 呈现方式 | 一张建议卡片，**写明依据**："这 3 天晚上的药都是 20:40 之后才确认的。要不要把晚上的提醒提前到 19:30？" |
| 用户纠正 | 卡片下方"有用 / 没用"两个按钮；点"没用"直接展开一句话反馈，不强制 |
| 失败/不可信处理 | ① 数据不足（<3 天）→ 不出建议，避免瞎猜；② 建议**永不自动执行**，家属点了"改成 19:30"之后必须走老人确认，老人确认前老人端时间不变 |
| 明确不做 | 不做自动改时间；不做多方案对比；不引用任何医学依据 |

### AI 的边界（写进产品，不藏在文档里）

- 老人端每一句话都会**原样复述**给老人听/看，老人永远知道系统听到了什么。
- 家属端所有 AI 产出都带"这是建议/识别结果，需要确认"的标注，且**改任何设置都要老人点头**。
- AI 不判断病情、不给用药意见、不代替女儿做决定。

## 六、产品验证与原型走查

### 6.1 指标

| 类型 | 指标 | 统计对象 | 计算口径 | 观察周期 |
|---|---|---|---|---|
| **核心成功指标** | **核心任务按时完成率**（目标 24 小时内 ≥ 85%） | 绑定家属的独居老年用户 | 当日应办事务中，在计划时间 ±30 分钟内（截止型事务在截止前）被确认为"已完成"的比例 | 上线后 4 周 |
| 过程指标 1 | 家属平均响应时间 | 触发家属通知的事件 | 家属首次回应时间 − 通知发出时间 | 4 周 |
| 过程指标 2 | AI 识别纠错率 | 所有语音识别事件 | 用户点"不对/修改"的次数 ÷ 识别总次数 | 4 周 |
| 过程指标 3 | 提醒确认率 | 所有已触发的提醒 | 被确认（完成/取消/求助）的提醒 ÷ 已触发提醒 | 4 周 |

> 不把预期值写成实测结果：以上均为**计划中的口径**，原型阶段无真实数据。

### 6.2 怎样发现误导建议、操作失败等问题

- **AI 建议自带反馈闭环**：每张建议卡片底部固定"有用 / 没用"双按钮，"没用"展开一句话反馈 → 误导建议直接体现在"没用"率上。
- **一致性回执**：家属改了提醒时间，老人端必须有"女儿改了晚上的提醒 → 19:30，你同意吗"的确认页；老人没确认前老人端时间不变 → 静默修改会被老人直接发现。
- **失败可上报**：语音识别连续失败、按钮无响应等，老人端底部常驻"找女儿帮忙"入口，可顺带说明"刚才那个说话的听不清"。
- **走查**：见《04-走查记录.md》，覆盖正常完成 / 修改取消 / 失败无法继续 三条路径，以及老人↔家属角色协作。

### 6.3 最小验证方法与下一步迭代依据

- 最小方法：找 3–5 位有独居长辈的家庭，用本原型（预置角色 + 模拟状态）做 20 分钟任务走查，记录"第几步卡住 / 哪句话看不懂"，不追求统计显著性。
- 下一步迭代依据：哪一步卡住率最高就改哪一步；若语音识别纠错率 > 40%，把按钮确认提到语音之前作为默认。
