# 安安 · 独居老人生活事务提醒与家人协作

> 110 实验室招新考核（2026 秋季）· 产品岗
> 题目：**面向老年人的 AI 日常事务与家庭协作助手**

**一句话定位**：让不会用智能手机的老人"听得懂、点得动、有人接手"地完成每天那几件必须做的事，并让外地子女只在需要时被叫到。

---

## 1. 项目背景

老年人在日常生活中经常需要：

- 提醒自己按时吃药
- 提醒自己取快递
- 提醒自己缴纳水费
- 在遇到困难时向家人求助

这些事情看似简单，但对部分老人来说存在三个明显障碍：

1. **入口复杂**：提醒功能藏在多层菜单里，老人找不到。
2. **反馈不清楚**：系统说了什么、是否听懂、下一步该做什么，老人不知道。
3. **缺少协作**：老人漏做或不会操作时，家属无法及时接手。

现有产品往往解决了"看得见"或"有提醒"，但没有解决：

> 老人听不懂、点不动、出问题时没人接手。

因此，本项目围绕一个具体问题展开：

> **老人需要一个能听懂日常事务、能确认理解、遇到问题时能请家人协助的生活事务提醒工具。**

## 2. 目标用户

### 老人端：张桂兰，72 岁，独居

- 独居，子女定居外地
- 每周与子女视频通话一次
- 只会接打电话、用微信发语音
- 不会打字，看不懂复杂 App
- 经常记错吃药时间、忘记取快递和缴费
- 怕"点坏了"，也怕麻烦女儿

**设计影响**：

- 老人端以语音和大按钮为主
- 文案必须短、直白、接近生活表达
- 每一步都要明确告诉老人"发生了什么、接下来能做什么"
- 家属参与不能让老人产生被监控或被责备的感觉

### 家属端：张莉，40 岁，女儿

- 在外地工作，工作日时间有限
- 熟练使用智能手机
- 希望能远程帮妈妈录入待办
- 希望只在异常时收到提醒
- 不希望正常完成情况不断打扰自己

**设计影响**：

- 复杂操作放在家属端
- 家属默认只接收异常
- 正常完成只进入记录，不主动打扰
- 家属修改老人事务时必须经过老人确认

## 3. 本次产品范围

### 主问题

围绕一个日常事务问题展开：

> **生活事务提醒 + 超时后的家人协作**

### 纳入范围

| 事务     | 类型     | 提醒方式            |
| -------- | -------- | ------------------- |
| 服降压药 | 每日循环 | 每天 08:00、20:00   |
| 取快递   | 截止型   | 到驿站后 3 天内提醒 |
| 缴水费   | 每月截止 | 每月 15 日前提醒    |
| 买菜     | 每周循环 | 每周二 09:30        |

### 核心能力

1. 家属语音录入待办
2. AI 识别并复述识别结果
3. 老人通过语音或大按钮确认完成
4. 超时未完成时通知家属
5. 老人主动向家属求助
6. 家属回应、改期或标记已联系
7. 老人确认家属的修改
8. 取消、失败、网络异常和家属未回应的兜底处理

### 明确不做

- 智能药盒硬件
- 跌倒检测
- 定位监控
- 医疗诊断
- 紧急呼叫 120
- 真实网购和在线缴费
- 多老人管理
- 完整陪聊平台

本原型只验证一个有价值的用户流程，不扩展成完整养老平台。

## 4. 核心流程

### 4.1 家属录入待办

```text
家属打开家属端
  ↓
选择"帮妈妈记一件事"
  ↓
说一句要记录的内容
  ↓
AI 识别并复述
  ↓
家属确认或修改
  ↓
待办进入老人端
```

### 4.2 老人完成事务

```text
到点后，老人端出现全屏提醒
  ↓
老人听到语音播报并看到大字提示
  ↓
老人选择：
  - "我做完了"
  - "用语音说"
  - "叫女儿帮忙"
  ↓
系统复述理解结果
  ↓
老人确认"对"或"不对"
  ↓
状态更新
```

### 4.3 超时后家人协作

```text
老人 30 分钟未确认
  ↓
系统再次提醒
  ↓
老人仍未确认
  ↓
系统通知女儿
  ↓
女儿查看请求并回应
  ↓
老人收到结果回执
```

家属未回应时，老人端不会无限等待，而是提供：

- 打电话给女儿
- 找社区医生
- 继续等待
- 取消求助

## 5. 关键设计原则

### 5.1 适老交互

- 老人端正文使用大字号
- 主按钮足够大、对比度足够高
- 避免复杂层级和多步表单
- 文案使用老人熟悉的表达
- 语音识别失败时提供按钮替代路径

例如使用：

> "该吃药了"

而不是：

> "用药提醒任务待处理"

具体排版基线：老人端正文 ≥ 28px、主按钮高 ≥ 78px、对比度 ≥ 4.5:1、无键盘输入；家属端正文 16px、按钮高 ≥ 46px。
老人端设置页另提供"字再大一点"开关，可再放大一档。

### 5.2 状态透明

老人必须知道：

- 系统听到了什么
- 系统准备做什么
- 是否已经通知女儿
- 女儿是否回应
- 当前事务是否完成

AI 识别结果不会直接写入状态，必须经过老人确认。

### 5.3 权限边界

家属默认只能看到：

- 今日待办
- 完成或未完成状态
- 老人主动发起的求助
- 老人明确允许共享的内容

默认不共享：

- 位置
- 通话记录
- 其他 App 数据
- 老人的全部隐私信息

家属修改提醒时间时，必须经过老人确认。

### 5.4 异常处理

原型覆盖：

- 语音识别有误
- 连续听不清
- 网络失败
- 老人取消任务
- 家属撤回请求
- 家属未回应
- 数据不足时不生成建议

## 6. AI 规则

本项目中的 AI 不是自由聊天助手，而是嵌入具体业务流程的辅助能力。

### AI 介入点 1：家属端语音录入

- 输入：家属本次语音内容
- 输出：结构化待办复述（结构化字段 + 原始语音对照）
- 规则：家属确认后才生效
- 纠错：可修改时间、事项或删除识别结果
- 失败：保留原始语音并提供手动填写入口

### AI 介入点 2：老人端语音反馈

- 输入：老人对当前事务的语音反馈
- 输出：系统复述理解结果
- 规则：老人点击"对"后才写入状态
- 纠错：点击"不对"进入纠错页
- 失败：连续失败后提供"改成按按钮"

### AI 介入点 3：家属端改期建议

- 输入：最近几天的事务确认时间
- 输出：建议卡片（写明依据，如"这 3 天晚上的药都是 20:40 之后才确认的"）
- 规则：只在数据足够时出现
- 规则：建议永不自动执行
- 规则：家属提出修改后仍需老人确认

### AI 边界

- 不判断病情
- 不提供医学建议
- 不代替老人或家属做决定
- 不在未确认前修改老人端状态
- 不把 AI 生成内容写成真实用户调研证据

## 7. 验证方案

### 核心成功指标

**核心任务按时完成率**

> 在计划时间 ±30 分钟内被确认为"已完成"的事务比例

目标：上线后 4 周达到 85% 以上。

### 过程指标

| 指标             | 统计对象           | 计算方式                           |
| ---------------- | ------------------ | ---------------------------------- |
| 家属平均响应时间 | 触发家属通知的事件 | 家属首次回应时间 − 通知发出时间    |
| AI 识别纠错率    | 所有语音识别事件   | 点击"不对/修改"的次数 ÷ 识别总次数 |
| 提醒确认率       | 所有已触发提醒     | 已确认提醒数 ÷ 已触发提醒数        |

> 以上均为**计划中的口径**，原型阶段没有真实数据，不把预期值写成实测结果。

### 最小验证方法

找 3–5 位有独居长辈的家庭，使用本原型进行 20 分钟任务走查，记录：

- 第几步卡住
- 哪句话看不懂
- 哪个反馈不清楚
- 哪个角色切换让人困惑

### 自行走查路径

1. 正常完成流程
2. 修改或取消流程
3. 失败或无法继续流程
4. 老人与家属之间的协作流程

实际走查结论与缺陷修复记录见 [`docs/04-走查记录.md`](docs/04-走查记录.md)；
可用 [`tools/walkthrough.js`](tools/walkthrough.js) 自行复现（真实点击式自动走查，90 项断言）。

## 9. 快速开始

### 方式 A：Docker（评审推荐）

```bash
docker compose up --build
```

启动后访问：

```text
http://localhost:8080
```

停止：

```bash
docker compose down
```

### 方式 B：静态服务

原型是纯静态站点，不需要构建步骤。

```bash
python -m http.server 8080
```

或：

```bash
npx serve -l 8080
```

然后访问：

```text
http://localhost:8080
```

> 也可以用任意静态服务器托管本目录。原型使用 hash 路由（`#/elder/home` 这种），**不需要服务端 rewrite 配置**。

### 端口与访问地址

| 项 | 值 |
|---|---|
| 容器内端口 | `80` |
| 宿主机映射端口 | `8080`（见 `docker-compose.yml`） |
| 默认访问地址 | **http://localhost:8080** |
| 若 8080 被占用 | 改 `docker-compose.yml` 里的 `"8080:80"` 左值，例如 `"8081:80"`，然后访问 `http://localhost:8081` |

### 常见启动问题

| 现象 | 原因与处理 |
|---|---|
| `docker compose up --build` 报端口被占用 | 8080 已被别的程序占用。改 `docker-compose.yml` 的 `"8080:80"` 为 `"8081:80"`，访问 `http://localhost:8081` |
| `docker: command not found` | 本机未安装 Docker。可改用「方式 B」的静态服务，效果完全一致（前端不依赖容器） |
| 首次 `--build` 较慢 | 需要拉取 `nginx:1.27-alpine` 基础镜像（约 20–50 MB，取决于网络） |
| 页面打开是旧画面 | 已在 `nginx.conf` 里对 html/css/js 禁用缓存；如仍异常，强制刷新（`Ctrl/Cmd + Shift + R`） |
| 画面停在某个异常状态 | 点演示控制条「↺ 恢复初始状态」，或刷新页面 |
| 容器起来了但页面 404 | 确认是从**本仓库根目录**执行 `docker compose up`（`build: .` 依赖当前目录） |

### 自检命令

```bash
# 1. 容器是否健康
docker compose ps

# 2. 首页是否可访问
curl -I http://localhost:8080

# 3. 静态资源是否齐全
curl -o /dev/null -w "%{http_code}\n" http://localhost:8080/css/app.css
curl -o /dev/null -w "%{http_code}\n" http://localhost:8080/js/app.js

# 4. 自动走查（可选，需要 Node + Chrome；真实点击页面，90 项断言）
cd tools && npm install && node walkthrough.js
```

## 13. 项目边界

本项目明确没有实现：

- 后端业务逻辑
- 数据库
- 真实 AI 模型调用
- 真实短信、电话或微信推送
- 真实语音识别
- 医学诊断或用药建议
- 智能硬件接入

所有 AI 结果、语音识别、网络失败、计时和家属回应均为前端预设状态模拟，用于验证产品流程和交互设计。
